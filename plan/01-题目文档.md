# 10-20-sqltrace · SQL 值/控制双通道血缘 + 写入者普查 + diff 闸门（题目文档）

> - **性质**：不参赛项目题（无赛事锚点；含金量锚点 = 竞品实测边界 + 六条真实解析器丢列 issue + 三个检索式为 0 的切口 + 需求侧原话）
> - **目标产出**：仓库 `10-20-sqltrace`（SQLTrace），发布 GitHub **公开仓库**，署名 `yuluo554`
> - **版本史**：v1 2026-10-20（初稿定稿；竞品与检索**基准日 2026-10-20**，GitHub API 返回时间戳 2026-10-19T17:50Z，即北京时间 2026-10-20 01:50）
> - **交付形态**：**纯本地 Python CLI**（唯一形态）。**无数据库连接、无元数据平台、无服务端、无网络请求**。不做图形界面，不做 Web 服务，不做桌面窗口。
> - **定位宣言**："离线列级血缘**不是空白**——FlowScope 105★ 已占。但它没做三件事：①**值边 vs 控制边不分**（sqlglot 实测把窗口分区键与值参数并列成同层下游、不标类型；sqllineage 的谓词血缘 issue 挂了四年）②**没有写入者普查/多写冲突**③**没有 git 维度的血缘 diff 闸门**。本工具只押这三件，验收基准里的'精确率 100%、零静默、五条 golden 回归'是全部护城河。"
> - **诚实定位**：本题不宣称"离线列级血缘首创"，也不宣称"SQL 解析首创"。**"离线纯本地"这个位置已被 FlowScope 占住**，且它比多数人以为的深（14 方言、DDL schema、dbt/Jinja 预处理、近似标记、错误码、Impact X-Ray）。本题的全部差异只在三个切口上，其余能力一律承认是跟随（见 §六）。
> - **品牌隔离**：本题只做 SQL 血缘与普查工具；不复用本系列任何其他工具的命名、代码、素材与文档模板，本文档不提及本系列其他项目。

**从实测表直接读出的三个切口**：

1. **值 vs 控制不分**：sqlglot 把 `PARTITION BY k` 与值参数 `x` 并列成下游节点（`w` 的两个下游是 `t.x` 与 `t.k`，不带任何类型标注）——分区键不改变输出值，只改变分组，**在语义上属于控制而非取值**；sqllineage 的谓词血缘 #276 自 2022-07-20 开至今未做。**这不是"没做"，是"做错了"**，所以修法必须是**类型分型**，而不是再补一层模糊匹配。
2. **没有写入者普查**：竞品输出的都是"某列从哪来"，没有人回答"这张表被几个文件、几条语句写过、哪两个写入者在抢同一张表"。`sql table multiple writers conflict` / `sql ownership conflict` 检索均返回 **0**。
3. **没有 git 维度的血缘 diff 闸门**：rocky 307★ 有 lineage-diff，但它绑定 dbt 生态；`sql folder git diff lineage` 检索返回 **0**，`lineage regression test golden` 返回 **0**。

### 1.5 原型已验证（✅）

单文件原型已跑通链路：**多文件语料 → 列级边 → 反向影响查询 → 两版本 lineage diff**。实测：v1 三条边 → v2 上游换源 → 输出 `REMOVED` / `ADDED`。这证明"diff 闸门"不是纸面设计，但它只是原型，**不含 M2 的类型分型、M3 的 reason code、M4 的普查**——这三样才是本题要做的事。

### 1.6 为什么是工具，而不是"问 LLM"

- **LLM 聊天读不了你的整个 SQL 目录**：本题要遍历目录、尊重 `.gitignore`、按拓扑排序推导 schema、对两万行语料给出**逐边可复算**的结果。聊天窗口里贴不进去，也复算不了。
- **LLM 聊天给不出"零静默"**：它不会因为"这列我推不出来"就拒绝输出，它会编一个最像的列名。本题的底线是**宁可 `unknown` 不得假边**。
- **LLM 聊天进不了 CI**：`lineage diff --base` 要在 PR 里给退出码。这是**确定性测量基建**，不是问答。

## 二、任务要求

首期 **5 个模块**，扩展项另列。每模块写清 **输入 / 输出 / 确定性纪律 / 验收**。所有数值口径（三类边定义、reason code 枚举、精确率/召回判定、退出码、方言列表）**只在 `data/README.md` §四定义一次**，代码、文案、文档一律引用该节，不得另立第二套口径。

**全项目确定性纪律（五条，每模块都适用）**：
1. **不用任何模糊匹配**：不允许正则拼列名、不允许编辑距离、不允许"最相似列名"、不允许隐式同名推断。所有边来自 AST 节点与 scope 绑定。
2. **宁可 `unknown` 不得假边**：推不出就标 unknown 并给 reason code，**不得静默跳过**，也不得猜。
3. **零网络**：运行期不发任何请求（不查 PyPI、不查 GitHub、不传遥测）。
4. **稳定排序**：所有输出按 `(target_table, target_column, kind, source_table, source_column, expr)` 字典序排序，同输入两次运行**字节级一致**。
5. **单一入口**：所有能力只由 `sqltrace` 一条命令树暴露，库 API 不作为验收路径。

### 模块①：语料装载 + schema 推导

- **输入**：一个目录（含 `.sql` 文件，可多层嵌套）；可选 `--schema <ddl.sql>` 外部 schema 覆盖；可选 `.gitignore`。
- **输出**：`corpus` 结构——文件清单（相对路径 + 内容哈希 + 方言）、按拓扑排序的语句序列、推导出的表 schema（`table → column[]`，含未知标记）。
- **引擎**：
  - 目录遍历**尊重 `.gitignore`**（含嵌套与取反规则），跳过 `.git/`；
  - DDL 语句（`CREATE TABLE`）直接产出 schema；
  - `CREATE TABLE AS SELECT` / `CREATE VIEW ... AS SELECT` **正向传播**：由 SELECT 的输出列推导目标表列名与类型（类型未知则标 unknown，不编造）；
  - 语句间依赖按**拓扑排序**（视图/中间表先建后用；检测环并报 `cycle_detected`，不静默丢弃）；
  - 外部 `schema.sql` **覆盖**同名表的推导结果，并在诊断里记录"覆盖了哪张表"。
- **确定性纪律**：文件遍历结果按路径排序；拓扑排序在同层按文件路径 + 语句序号排序；schema 推导不依赖 `glob` 返回顺序、不依赖字典插入顺序。
- **验收**：给定多文件语料（含嵌套目录、含被 `.gitignore` 排除的文件、含跨文件视图依赖），解析结果**无遗漏**——每个 `.sql` 文件都在 `corpus.files` 里出现一次且仅一次，被忽略的文件出现在 `corpus.ignored` 并带原因。

### 模块②：确定性列血缘内核

- **输入**：M1 的 `corpus` + schema。
- **输出**：边集合。每条边含：`target_table`、`target_column`、`kind`（`value` / `control` / `unknown`）、`source_table`、`source_column`、`expr`（产生该边的表达式文本）、`join_path`（若经 JOIN 引入，记录连接链）、`aggregation`（是否经过聚合及函数名）、`window`（是否在窗口内及窗口函数名）、`statement_id`、`reason_code`（仅 unknown/降级时）。
- **三类边的定义**（口径在 `data/README.md` §四，此处为摘要）：
  - **`value`**：直接决定目标列取值的来源——SELECT 列表、表达式、聚合的参数、**窗口函数的值参数**（如 `SUM(x) OVER (...)` 里的 `x`）、CASE 的 THEN/ELSE 分支。
  - **`control`**：只影响"取哪些行 / 分组 / 排序 / 走哪条分支"，**不改变取值**——`WHERE`、`JOIN ... ON`、`GROUP BY`、`HAVING`、`OVER (PARTITION BY …, ORDER BY …)`、CASE 的 WHEN 谓词、`QUALIFY`。
  - **`unknown`**：无法在 AST 层面确定、且不能安全推断的来源（例如未知 schema 的 `SELECT *`）。**`unknown` 不是"其它"，它是显式交付物**。
- **引擎**：**sqlglot AST + 自研 scope walker**。sqlglot 只负责解析成 AST；**scope 解析、列绑定、边生成全部自研**——因为实测 sqlglot 的 `lineage()` 会把窗口分区键当值输入、遇到 `INSERT` 列清单直接报错、多语句直接拒绝，无法在其上打补丁得到正确分型。
- **确定性纪律**：AST 只读不改写；不调用 sqlglot 的 `lineage()` / `qualify()` 作为判定路径（可作为对照基准）；边去重键 = 全字段元组。
- **验收**：
  - **`value` 边精确率 100%**（人工标注语料上，任何一条 value 边错判即 FAIL）；
  - **召回 ≥ 85%**（未召回的部分必须落在 `unknown` 且带 reason code，不得凭空消失）；
  - `SUM(x) OVER (PARTITION BY k)` 必须产出 `value: w <- x` 与 `control: w <- k` 两条边，**不得**产出 `w <- k` 的 value 边。

### 模块③：降级策略引擎

- **输入**：M2 的内核在遇到"不能直接解"的构造时的钩子。
- **输出**：要么展开后的边，要么 `unknown` 边 + **机器可读 reason code**。**绝不静默。**
- **策略表**（每档都必须产出 reason code）：

| 构造 | 策略 | reason code / 标记 |
|---|---|---|
| `SELECT *` + schema 已知 | 展开为具体列 | 无（正常路径），诊断记 `wildcard_expanded` |
| `SELECT *` + schema 未知 | 产出 `unknown` 边，**不猜列名** | `unknown_wildcard` + `approximate=true` |
| CTE / 子查询 | 递归解析 + 逐层展开 | 无；层数超限则 `recursion_limit` |
| `UNION` / `UNION ALL`，两侧别名一致 | 按名合并 | 无 |
| `UNION` / `UNION ALL`，别名不一致 | 按位置合并 | `positional_union` |
| 窗口函数 | 值参数走 `value`，`PARTITION BY` / `ORDER BY` 走 `control` | 无（**修正 sqlglot**） |
| `INSERT INTO dst (c1, c2) SELECT …` | 按列清单**位置映射** | 列数不符则 `arity_mismatch` |
| `MERGE … UPDATE SET` | 逐列解析；不支持的分支 SKIP | `skipped_merge_branch` |
| `CREATE VIEW v(c1, c2) AS …` | **显式列名对齐**（OpenMetadata #33077 的坑） | 列数不符则 `arity_mismatch` |
| 存储过程体 | 只解静态 DML；遇 `EXEC` / `EXECUTE IMMEDIATE` 停 | `UNSUPPORTED_DYNAMIC_SQL` |
| 解析失败 | 定位到行列 + 跳过**该语句**，**不产出任何边** | `PARSE_ERROR` |

- **确定性纪律**：reason code 是**枚举**，不是自由文本（枚举在 `data/README.md` §四）；诊断项排序规则与边一致；同一条语句不得既产边又静默丢弃。
- **验收**：`grep -c unknown` 得到的 `unknown` 边数与诊断里的未解析计数**完全一致**；语料中每个降级构造都能在诊断里找到对应 reason code；**零静默**（不存在"解析了但没有任何输出也没任何诊断"的语句）。

### 模块④：写入者普查 / 冲突检测

- **输入**：M1–M3 的边集合 + 语句元数据。
- **输出**：Markdown 报表 + `--json` 结构：
  - `writers`：每张表 → 写入者列表（**文件路径 + 语句序号 + 方言**）；
  - `readers`：每张表 → 读取者列表；
  - `orphan`：**有读无写**的表（下游在用，但本目录没人产出它）；
  - `multi_writer`：**被 ≥2 个写入者写同一张表**的冲突项；
  - `write_only`：**只写不读**的表（产出后无人使用）。
- **引擎**：以"目标表"为键聚合写入来源；"多写"判定只看**写同一张表**，不猜测语义冲突（同名同列不算冲突、不同列也算同表冲突，判定口径在 `data/README.md` §四）。
- **确定性纪律**：报表条目按表名排序，同一表内写入者按文件路径 + 语句序号排序；不输出"冲突概率""风险分"之类的推断值。
- **验收**：合成语料中植入的多写冲突与孤儿表**全部命中**，且**无误报**（单写入者表不得出现在 `multi_writer` 里）。

### 模块⑤：lineage diff 闸门 + 输出

- **输入**：`--diff <base>`（git ref，如 `HEAD~1`、`main`，或第二个目录路径）。
- **输出**：
  - **边级 diff**：`ADDED` / `REMOVED` / `CHANGED`（CHANGED 指同 `(target, column, kind)` 的来源集合变化）；
  - **CI 退出码**：`0` 无变化 / `1` 存在 REMOVED（破坏性）/ `2` 仅 ADDED 或 CHANGED（非破坏）/ `3` 解析或配置错误（退出码语义在 `data/README.md` §四单点定义）；
  - **JSON**（稳定排序）+ **Markdown 评论**（可直接贴 PR）；
  - 反向影响查询：`sqltrace impact <table>.<column>` 输出上游来源与下游消费者，**穿透中间表**；
  - Mermaid 仅作为 Markdown 里的附加块，**不做图形产品**。
- **引擎**：git 模式用 `git show <ref>:<path>` 取基线语料（不切工作区、不改仓库）；双目录模式直接读两个目录。两种模式喂同一个内核。
- **确定性纪律**：JSON 键序固定（按 `(target_table, target_column, kind, source_table, source_column)` 排序），时间戳/绝对路径不进输出；同一次提交在两个平台上运行结果**字节级一致**。
- **验收**：
  - 同一输入连续两次运行，JSON **字节级一致**；换行与编码固定（`\n`，UTF-8 无 BOM）；
  - `impact raw.cust.nm` 能**穿透 2 层中间表**给出最终消费者；
  - 五条 golden 回归（见 §三）全绿。

### 扩展项（不进首期）

- **存储过程体内静态 DML**：sqlglot 实测对 `CREATE PROCEDURE` 只能给 Block 包装，T-SQL 的 `GO` 直接 `ParseError`；一周内做不出可信结果，必然靠启发式从而违背"确定性内核"，留扩展项。
- **更多方言**：首期限定 5 种（PostgreSQL / Snowflake / BigQuery / T-SQL / DuckDB），其余留扩展项。
- **交互式 UI**：**明确不做**（见 §六）。

## 六、边界与非目标

- **不做交互式血缘图 UI**：撞 FlowScope 的 Impact X-Ray 与 SQL Crack（171★），且属可视化禁区。输出只有 JSON + Markdown（Mermaid 为附加块）。
- **不做 `SELECT *` 的逆向推导**：FlowScope / sqllens 的领地；本题在 schema 未知时**只标 `unknown_wildcard`，不猜列名**。这是刻意的能力边界，不是缺陷。
- **不做存储过程体内血缘（首期）**：sqlglot 实测对 `CREATE PROCEDURE` 只能给 Block 包装、T-SQL `GO` 直接 `ParseError`；一周内做不出可信结果，必然靠启发式从而**违背确定性内核**。
- **不做元数据平台对接**：不接 DataHub / OpenMetadata / Atlas / OpenLineage，不产出它们的格式。
- **不做数据库连接**：不连任何库、不读 `information_schema`、不用 `--sqlalchemy_url` 这类入口。schema 只来自本目录 DDL 或 `--schema` 文件。
- **不做 dbt 项目解析**：不读 `dbt_project.yml`、不展开 Jinja。只吃纯 SQL（这是与 FlowScope 的明确分工）。
- **不做排名 / 打分**：普查输出是事实（谁写了、谁读了），不是风险评分。
- **隐私红线**：SQL 语料**纯本地零网络**——运行期不发任何请求、不写任何外部路径、不读取语料目录之外的文件（`--diff` 的 git 调用除外，且只读）。
- **品牌隔离**：不与本系列其他 CLI 工具共享命名、代码、素材与文档模板。
- **首期范围限定**：5 个模块 + **5 种方言**（PostgreSQL / Snowflake / BigQuery / T-SQL / DuckDB）+ 40–60 个标注语料文件 + 五条 golden。存储过程、更多方言、UI 全部留扩展项或明确不做。
- **结论纪律**：`value` 边精确率 100% 是**在人工标注语料范围内**的判定，不是"对任意 SQL 100% 正确"；召回 ≥85% 同理。文档与 README 必须写明该口径，不得暗示普适完备。
